# 待确认问卷(按负责人拆分)

版本:v0.4  日期:2026-11-09(与 PRD v0.4 §10 同步)
用法:产品把对应部分发给各负责人,收集答案后回填。每题标注"为什么要问"和"答不上来时怎么办"。
优先级:🔴 阻塞(不回答无法排期) 🟡 重要(影响方案) 🟢 一般(有默认值可先走)

> 变更说明(相对 v0.1):业务由写字课改为 Tutor Luna;新增法务/合规问卷;新增口径类、内容类、订单类问题;删除"班期/作业"相关问题。
> **原则**:口径未确认时,AI 不自行回答、转人工,相关内容不入库。所以下列口径问题**不回答也不会阻塞开发**,但会限制 AI 能做的事。

## 一、给研发 / 企微管理员

| # | 优先级 | 问题 | 为什么要问 | 答不上来时的默认处理 |
|---|---|---|---|---|
| R1 | 🔴 | 现在"加好友欢迎语"和"标签同步"分别是通过什么方式接入企微的?(自建应用 / 第三方服务商 / SCRM 工具 / 其他) | 决定可用接口,以及能否复用 | 假设自建应用,方案保持可替换 |
| R2 | 🔴 | 系统现在能不能收到外部用户发来的消息?通过什么方式(微信客服、会话存档、服务商回调)? | 没有用户消息就无法做智能回复 | 先做主动触达与标签,回复能力待通道确认 |
| R3 | 🔴 | 系统能不能自动给外部用户发 1 对 1 消息?有无次数或时间窗口限制?实测结果如何? | 官方资料显示存在限制(群发每月 4 条、微信客服 48 小时内 5 条,**待核实**),决定 SOP 能否全自动 | 设计成可降级:改为"生成内容+销售一键发送" |
| R4 | 🔴 | 业务后台用户和企微用户如何对应?(手机号 / unionid / 绑定流程) | 业务事件触发要知道对应哪个企微用户 | 映射失败的事件不触发,记录并告警 |
| R5 | ✅ 已承诺 | 业务后台提供**用户状态查询接口**:是否已开通体验课、是否登录过 APP、首次到课、完课、学习报告数据。**产品已安排研发在项目开始前提供**,接口字段见本文第七部分;事件推送(webhook/消息队列)是否同步提供待研发确认 | 待到课、回访、课后反馈都依赖;"催下载/催登录"要判断状态;回答"进不去"类问题以此为准 | 研发在项目启动前交付;未交付前不影响设计,联调时用模拟数据 |
| R6 | 🟡 | 当前标签同步的技术栈、部署方式、是否有测试环境、事件来源 | 新模块是否同栈、能否订阅阶段/状态事件 | 假设 Python,独立服务 |
| R7 | 🟡 | 抖音订单状态能否通过接口获取?(订单创建、支付、退款) | 关单后判断是否成交、何时停止催单 | 先由销售手动回填 |
| R8 | 🟡 | 模型选型限制:可用厂商,是否允许把用户消息/图片发往外部 | 合规与成本 | 国内模型,脱敏后调用 |
| R9 | 🟡 | "植入课程/开通体验课"是人工还是系统自动?如何触发? | 邀约到待到课衔接,事件来源 | 假设有"已开通"事件 |
| R10 | 🟡 | 进线时的"信息表"字段有哪些?数据存在哪里?能否读取? | 决定挖需阶段能少问什么 | 暂不依赖,对话中补采集 |
| R11 | 🟢 | 预期规模:单销售号用户数、峰值消息数/秒 | 容量设计 | 单号 ≤ 2000,峰值 20 条/秒 |
| R12 | 🟢 | 向量数据库是否已有可用资源 | 知识库选型 | 建库时再定 |
| R13 | 🟢 | 日志与会话保留期要求 | 存储与合规 | 180 天 |

## 三、给法务 / 合规 / 课程运营(新增)

这一部分对应《08》里发现的矛盾与风险。**每一项只要给出"可以说/不可以说/怎么说"的一句话结论即可。**

| # | 优先级 | 问题 | 背景 | 默认处理 |
|---|---|---|---|---|
| L1 | 🔴 | **AI 是否需要向用户明示身份?**以什么方式(固定自我介绍/首次说明)? | 现有话术销售以"Luna 老师"自称 | 默认首次明示"智能助手",待确认 |
| L2 | 🔴 | **退款政策**对外口径:7 天无理由的条件、办理渠道(抖音)、到账时效 | 话术有"当天到账""极速秒退""全额免责"等确定承诺,与平台实际规则可能不符 | AI 不承诺时效,只说"转人工协助办理" |
| L3 | 🔴 | **价格与优惠**对外口径:课包价格、优惠券 1100、抖音满减、实付 2250 的构成,是否固定、有效期 | 3699−1100≠2250,构成不清 | AI 不报价,转人工 |
| L4 | 🟡 | **正式课新版升级时间**:话术一处说"下周升级",另一处说"已完成升级",以哪个为准 | 前后矛盾 | 不提升级时间 |
| L5 | 🟡 | **模型来源/技术架构**能否对外说(腾讯/自研/DeepSeek/Qwen)?"自研"的说法是否准确 | 话术与第 7 页技术图表述不一致 | 不提及,问到转人工 |
| L6 | 🟡 | **统计类表述**(如"86%同学完课""平均开口 57 次")能否使用?数据来源是什么 | 话术中是写死的数字 | 不使用写死数字;仅用后台真实数据 |
| L7 | 🟡 | **"体验课价值 99 元"**的对外说法是否合规、有无依据 | 若用户实际免费领取,需核实表述 | 不使用 |
| L8 | 🟡 | **品牌名称**对外统一用 Tutor Luna 还是 LingoAce Luna Tutor | 资料中两种写法 | Tutor Luna |
| L9 | 🟡 | **"新课标重点要求"**等引用政策的表述是否有依据 | 话术中出现 | 不使用 |
| L10 | 🟡 | **礼品**相关表述(是否可转卖、折现)的口径 | 话术出现"挂咸鱼卖三四百" | 删除该类表述 |
| L11 | 🟡 | **"禁止承诺词表"**(效果、提分、退款到账、保证等) | 输出审核依据 | 先用保守词表 |

| L13 | 🟢 | 儿童个人信息(年龄、英语水平)的采集告知与授权方式 | 挖需会采集未成年人相关信息 | 采集前不做额外说明,待合规意见 |

## 七、给研发的接口需求清单(对应 R5,产品已承诺项目开始前交付)

> 目的:让 AI 和提醒系统能准确知道"这个家长现在到哪一步了"。以下是**产品侧的需求**,技术形式(接口协议、字段命名)由研发定。

### 7.1 查询接口(必须)
**入参**:业务用户标识(手机号或业务用户 ID,见 7.3 的对应关系问题)。

**出参**:
| 信息 | 说明 | 用在哪 |
|---|---|---|
| 用户是否存在 | 区分"没报名"和"报名了但没开通" | 回答"进不去"类问题 |
| 是否已开通体验课 + 开通时间 | 销售是否已"植入课程" | 邀约→待到课的迁移;提醒判断 |
| 体验课到期时间 | 有效期约 4 天(待确认) | 到期前提醒 |
| 是否登录过 APP + 首次/最近登录时间 | 用报名手机号登录 | 区分催下载 / 催登录 |
| 设备类型 | 平板/手机/其他 | 不支持电脑/学习机的提示 |
| 首次到课时间 | 第一次进入上课 | 阶段迁移到"到课未完课回访" |
| 已完成节数、是否完课、完课时间 | "完课"口径待确认 | 阶段迁移;课后反馈 |
| 学习报告关键数据(如开口次数) | 用于课后反馈话术的真实数据 | 避免话术里写死数字 |

### 7.2 非功能要求
| 项 | 要求(初稿) |
|---|---|
| 实时性 | 状态变化后分钟级可查到(登录、到课、完课越快越好) |
| 明确的结果 | 查不到时明确区分"用户不存在 / 未开通 / 查询失败",不能都返回空 |
| 稳定性 | 失败有明确错误码;支持限流说明 |
| 鉴权与安全 | 仅内部系统可调用;返回的个人信息做最小化 |
| 环境 | 提供测试环境和测试数据,便于联调与评测 |

### 7.3 一个常被忽略的前提:账号对应关系(R4)
接口按"业务用户"查询,而 AI 面对的是"企业微信里的家长"。**必须有办法从企微家长对应到业务用户**,否则接口查不到人。常见方式:
- 家长在信息表里填的手机号 ↔ 报名手机号;
- 销售在后台开通时,绑定企微账号;
- 其他由研发提出的方案。
这一项与 R5 同样重要,建议和 R5 一起交付。

### 7.4 可选(有则更好)
- 事件推送:状态变化时主动通知(开通、登录、首次到课、完课),这样提醒不用靠轮询。
- 抖音订单状态查询(R7)。

### 7.5 交付前的联调约定
- 研发在项目启动前提供接口文档和测试环境。
- 项目开始后的第一阶段,AI 与提醒功能先用**模拟数据**开发,接口就绪后切换,不阻塞进度。
